# C6　総合演習：小さく安全に拡張する

*Part C — 上級：UNIXを読んで改造する*

**この章の到達目標：** 観察で作った図を，改造・検証・文書更新へつなげる．

ここでは「カーネルを大きく改造できること」ではなく，**小さな変更の必要性を説明し，元に戻せる形で検証すること**を評価します．C1でユーザアプリ，C2で起動とタスク，C3でSVC・FD・VFS，C4でドライバを読みました．一つの機能追加がどの層に関わるかを判断します．

既存の仕組みで実現できるなら，新しいシステムコールを増やす必要はありません．仕様を調べる順序は[カーネル拡張ガイド](../../development/kernel/KERNEL-DEVELOPMENT.md)→必要に応じて[システムコール開発ガイド](../../development/syscalls/SYSCALL-DEVELOPMENT.md)または[ドライバ開発ガイド](../../development/drivers/DRIVER-DEVELOPMENT.md)です．

## C6.1 最初は変更しない設計を作る

新しい機能の前に，既存の`/proc/uptime`や`/proc/ticks`が何を返すか確認します．この情報を別APIでも公開する場合，「本当に新しい仕様が必要か」を説明してください．学習用に重複した機能を作る場合は**教材上の意図**を記録します．

## C6.2 比較対象を選ぶ

### 変更前に作るチェック表

| 確認項目 | 考えること |
|---|---|
| 目的 | 誰が何をできるようになるのか |
| 既存機能 | `/proc`や既存コマンドで代替できないか |
| インターフェース | 新APIか，既存APIの拡張か |
| 資源 | RAM・Flash・タスク・FD・ピン番号の影響 |
| 失敗時 | 不正引数や資源不足で何を返すか |
| 検証 | 通常時だけでなく境界値も試せるか |
| 文書 | 日英の正本をどこに置くか |

まずコードを変更せずに設計表を完成させ，その後に**一つだけ**変更します．`git diff`で変更箇所を説明できないほど広くなったら，作業を細分化してください．テストのPASSは実機動作を自動的に保証しないので，対象機材と確認した範囲を報告します．

[カーネル拡張ガイド](../../development/kernel/KERNEL-DEVELOPMENT.md)には，起動時間をシステムコールとデバイスノードで公開する**未検証の演習例**があります．まずシステムコール経路とVFS経路の両方を図にし，変更ファイルとABI・IDの衝突の確認項目を列挙します．掲載例は現在のソースで番号を再確認してから利用してください．

## C6.3 変更とテスト

実際に改造する場合は，Linux PC上で別ブランチを作り，一つずつ変更して差分を確認します．`python3 tools/run_tests.py`，可能なら`python3 tools/run_tests.py --all`とPico/Pico Wの実機試験を実施してください．ビルドのPASSだけでは実機での安全や動作が保証されません．

## C6.4 最終成果

**最終演習の進め方：** (1) まず変更不要の観察結果を記録する．(2) 新しいAPIが必要か判断する．(3) 変更ファイルと影響を表にする．(4) 変更後に同じ実験を繰り返す．(5) `git diff --check`と必要なテストを実行する．**提出物：** 変更前後の観察，変更差分，テスト結果，仕様の記述を1組にして，第三者が追試できるようにします．

次の4点を成果物にします．

1. **実行結果**：操作と観察の記録．
2. **実装の図**：ユーザAPI→SVC→FD/VFS→対象の経路．
3. **変更差分**：加えた機能，制約，テスト結果．
4. **文書**：更新した日英の仕様・学習ページ．

ここまで説明できれば，UNIXを**使う→観察する→読む→改造する**学習が一巡します．

学習の記録：**実行したこと／結果／その理由**を1〜3文ずつ書いてください．
