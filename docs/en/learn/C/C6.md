## C6.1 Design before editing

Inspect existing `/proc/uptime` and `/proc/ticks` before proposing a new uptime interface. Explain whether it is needed. A redundant API can still be useful as a **teaching exercise** when its reason is clear.

## C6.2 Compare extension paths

The [kernel development guide](../../development/kernel/KERNEL-DEVELOPMENT.md) contains an **unverified exercise** implementing uptime through a syscall and a device node. First diagram both paths and list ABI, ID, and path conflicts. Recheck IDs against the current sources before using example values.

## C6.3 Modify and test incrementally

Make a separate Git branch on the Linux host. Review each diff; run `python3 tools/run_tests.py`, then `python3 tools/run_tests.py --all` when feasible. Verify on Pico/Pico W hardware. A build/test PASS alone does not establish safe hardware behavior.

## C6.4 Final deliverables

Submit:

1. **Observations:** commands and outcomes.
2. **A flow diagram:** user API → SVC → FD/VFS → target.
3. **A tested diff:** changes, limitations, checks.
4. **Documentation:** updated Japanese and English behavior descriptions.

You have completed the cycle **use → observe → read → extend**.

Learning record: Write down **what you ran / what you observed / why it happened**.
