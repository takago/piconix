# C6　Capstone: extend the OS safely

*Part C — Advanced: Read and extend UNIX*

**Learning objective:** Turn observations and code reading into a testable design.

The goal is not to make the largest kernel change. It is to **justify a small change and verify it in a reversible way**. C1 explored applications, C2 boot and scheduling, C3 syscalls and VFS, and C4 drivers. Decide which layer, if any, actually needs a new feature.

If an existing `/proc` entry or program already satisfies the need, a new syscall may be unnecessary. Consult the [kernel extension guide](../../development/kernel/KERNEL-DEVELOPMENT.md) first and then, if needed, the [syscall guide](../../development/syscalls/SYSCALL-DEVELOPMENT.md) or [driver guide](../../development/drivers/DRIVER-DEVELOPMENT.md).

## C6.1 Design before editing

Inspect existing `/proc/uptime` and `/proc/ticks` before proposing a new uptime interface. Explain whether it is needed. A redundant API can still be useful as a **teaching exercise** when its reason is clear.

## C6.2 Compare extension paths

### Checklist before editing code

| Item | Question |
|---|---|
| Goal | Who needs to do what? |
| Existing capability | Can a current `/proc` entry or command do it? |
| Interface | New API or extension to an existing one? |
| Resources | Impact on RAM, Flash, tasks, FDs, and pins? |
| Failures | What happens for invalid input or exhausted resources? |
| Tests | Can normal and boundary cases both be checked? |
| Documentation | Which Japanese and English pages are authoritative? |

Complete the design table **before** editing, then change one thing at a time. If `git diff` is too large to explain, split the work. A passing build or scripted test does not automatically establish real-device behavior; report exactly what was tested.

The [kernel development guide](../../development/kernel/KERNEL-DEVELOPMENT.md) contains an **unverified exercise** implementing uptime through a syscall and a device node. First diagram both paths and list ABI, ID, and path conflicts. Recheck IDs against the current sources before using example values.

## C6.3 Modify and test incrementally

Make a separate Git branch on the Linux host. Review each diff; run `python3 tools/run_tests.py`, then `python3 tools/run_tests.py --all` when feasible. Verify on Pico/Pico W hardware. A build/test PASS alone does not establish safe hardware behavior.

## C6.4 Final deliverables

**Final exercise:** (1) Record baseline behavior; (2) justify a new API or rule it out; (3) list affected files/resources; (4) repeat the experiment after one small change; (5) run `git diff --check` and suitable tests. **Deliverable:** Baseline and result, patch, test evidence, and updated specification, sufficient for someone else to reproduce.

Submit:

1. **Observations:** commands and outcomes.
2. **A flow diagram:** user API → SVC → FD/VFS → target.
3. **A tested diff:** changes, limitations, checks.
4. **Documentation:** updated Japanese and English behavior descriptions.

You have completed the cycle **use → observe → read → extend**.

Learning record: Write down **what you ran / what you observed / why it happened**.
