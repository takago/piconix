# C4　Drivers: from VFS to hardware

*Part C — Advanced: Read and extend UNIX*

**Learning objective:** Understand the driver boundary before touching network code.

C3 followed an FD to an I/O target. This chapter examines the case where that target is a **peripheral device**. Keep the **physical circuit**, **device-file interface**, and **driver implementation** distinct; they require different documentation.

Start with the public contract in the [device reference](../../reference/devices/DEVICES.md), then use the [driver development guide](../../development/drivers/DRIVER-DEVELOPMENT.md) to locate the implementation. Physical wiring belongs to the [hardware reference](../../reference/hardware/README.md).

## C4.1 Begin with VFS

Find path dispatch and FD management in `kernel/kernel.c`; then inspect `kernel/gpio.c`, `kernel/fb.c`, `kernel/adc.c`, and `kernel/pwm.c`. Note which jobs belong to the VFS and which are hardware-specific.

## C4.2 Read/write and ioctl

### Choose just one device to read

For GPIO, identify what `/dev/gpio/N` represents, then trace path lookup and FD processing in `kernel/kernel.c` toward `kernel/gpio.c`.

| Question | Layer to inspect |
|---|---|
| Which path can be opened? | VFS and device registration |
| What does `read` / `write` exchange? | Public API and data format |
| How is pin direction configured? | `ioctl()` or similar controls |
| Which physical GP pin changes? | Driver and pin assignment |

Before attaching hardware, check the [pin reference](../../reference/hardware/PINS.md) for reservations by UART, PWM, or I²C. Reading driver source code requires no external wiring.

Device operations can share file APIs, but configuration often needs `ioctl()`. `/proc` exposes state rather than persistent storage. Keep **device drivers and networking as separate learning steps**.

## C4.3 Check before editing

Review the [driver development guide](../../development/drivers/DRIVER-DEVELOPMENT.md): path and ID conflicts, reserved pins, FD cleanup, and error returns. **Source reading is required; wiring or edits are optional**.

## C4.4 Reading assignment

**Source exercise:** Select one device and trace its path, VFS identification, driver entry, and physical pin or OS state. **Checks:** Invalid paths, unsupported I/O, and reserved pins. Physical wiring is not necessary for source reading. Keep the public device guide separate from the driver implementation guide.

Draw path → FD → VFS → device handler for one device.

1. Why might a device need `ioctl()`?
2. How does a device node differ from a regular file?
3. Which safety checks matter before hardware changes?

Learning record: Write down **what you ran / what you observed / why it happened**.
