# B1　File descriptors and VFS

*Part B — Intermediate: Observe UNIX*

**Learning objective:** Understand how files, terminals, and pipes share an I/O interface.

When you ran `echo hello | cat` in A2, `echo` did not need to know where its output would go. The key abstraction is the **file descriptor (FD)**: a small per-process number referring to an opened I/O target. FD 1 is **normally** standard output, not permanently the screen; the shell can redirect it.

The **virtual file system (VFS)** resolves paths and dispatches operations to files, devices, and virtual state entries. An FD is a number used *after opening* something; the VFS is the mechanism that connects names and operations to their implementation. Do not treat them as synonyms.

## B1.1 What is an FD?

A file descriptor (FD) is a **number** referring to an I/O object opened by a process. Typically, 0 is standard input, 1 is standard output, and 2 is standard error. Code can use `read()` and `write()` without knowing the destination’s concrete type.

## B1.2 Observe FDs

### Draw the FD connections

```text
standalone: cat FD 0 → terminal input; FD 1 → terminal output
pipeline:   cat FD 0 → pipe read end; FD 1 → terminal output
```

This is a **conceptual diagram**, not the entire internal FD table. `lsof` inspects open descriptors, but short-lived programs may have exited before you run it. That is not necessarily an error. The [pipe guide](../../guides/PIPE.md) explains the roles of `pipe()`, `dup2()`, and `close()` in constructing a pipeline.

The next chapter asks what happens when an FD refers to a terminal.

```text
piconix# lsof
piconix# echo hello | cat
piconix# ps
```

`lsof` displays FD ownership at a moment in time. A short-lived command may already have exited when you inspect it. The [pipe guide](../../guides/PIPE.md) explains `pipe()`, `dup2()`, and EOF.

## B1.3 A common namespace with VFS

The VFS resolves paths and dispatches operations to their implementation. A regular file in `/tmp`, a device in `/dev`, and a live view under `/proc` do **not** share the same storage backend, even though processes use similar APIs to access them.

## B1.4 Practice and check

**Guided experiment:** (1) Run `echo one | cat`; (2) draw “left FD 1 → pipe → right FD 0”; (3) inspect currently open FDs with `lsof`. **Common pitfall:** If the short-lived pipe descriptors are no longer visible, they may simply have closed when the commands exited. Absence from a later snapshot does not prove the pipe was unused.

Compare `cat /tmp/hello.txt` with `cat /proc/uptime` (recreate the RAM file if necessary).

1. Does FD 1 permanently mean a particular physical display?
2. Is a pipe stored like a normal RAM file?
3. What is shared by VFS, and what remains device-specific?
