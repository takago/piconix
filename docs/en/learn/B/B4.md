# B4　Observe system calls with trace

*Part B — Intermediate: Observe UNIX*

**Learning objective:** See the boundary between a user program and the kernel.

A3's `ps` answers **which tasks exist now**. `trace` helps answer **which system calls were made over time**. The two tools observe different things. Start with `hello` and find evidence that displaying text requires crossing from user code into the kernel.

**Terms:** A system call is a request from an application to the OS; SVC is the processor exception used to cross that boundary; PID identifies a task. See the [trace usage guide](../../guides/TRACE.md) for command behavior and output columns, and the [system-call reference](../../reference/SYSCALLS.md) for API arguments.

## B4.1 Form a hypothesis

`hello` can print text without manipulating the USB controller directly. An API such as `write()` delegates the output to the kernel. `trace` helps observe calls and returns.

## B4.2 Run trace

### Read your first `trace run` output

`trace run hello` **starts a fresh** `hello` process, waits for it to finish, and then displays events for that process. You do not need to know its PID in advance. It does not attach to an already running process.

| Column / event | Interpretation |
|---|---|
| Time | Event timestamp, not a value that must match across runs |
| PID / Command | Process associated with the record |
| `ENTER` | Entry to a system call |
| `EXIT` | Return from a system call |
| Call | Name of the operation, such as `write` |
| Ret / Data | Return value and limited captured data (not necessarily the entire payload) |
| `SWITCH` | An event related to task switching |

**Reading procedure:** (1) Notice the normal text printed by `hello`; (2) find matching `ENTER write` and `EXIT write` events; (3) inspect the return value. Multiple writes might separate a string from its newline, but use the source code in C3 to verify that interpretation rather than assuming it from a trace alone.

`trace show` displays recorded events and `trace follow` waits for new ones; **neither launches a target command**. Begin with `run`. Trace storage is a bounded ring buffer, so long runs may overwrite older events.

```text
piconix# trace run hello
piconix# cat /proc/uptime
piconix# ps
```

Look for `write()` events. PIDs, timestamps, and event ordering can vary between runs.

Next run `trace run ls` and compare it with `trace run hello`. `ENTER` and `EXIT` mark syscall entry and return, while `SWITCH` denotes task switching. Traces use a ring buffer, so older events may be overwritten. If using `lsof PID` to inspect a running task's descriptors, first identify the PID with `ps`. Values in `/proc/uptime` and `/proc/tasks` can change during observation.

## B4.3 Interpret the boundary

The C API leads to an SVC exception and the kernel’s dispatch path. You do not need to understand every source line yet. Draw the layers **user code → syscall ABI → kernel**.

## B4.4 Practice and check

**Guided experiment:** (1) Run `trace run hello` and note both normal output and trace records; (2) pair `ENTER write` with `EXIT write`; (3) repeat using `trace run ls`; (4) compare the call names. **Record:** Time, PID, Call, and Ret, then explain what each program asked the OS to do. Exact numeric values can change between runs.

Associate a displayed trace event with the program that generated it.

1. How does `trace` differ from `ps`?
2. How is a system call different from a normal C function call?
3. How is `write()` related to standard output?

Learning record: Write down **what you ran / what you observed / why it happened**.
