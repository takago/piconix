# B5　Devices as files

*Part B — Intermediate: Observe UNIX*

**Learning objective:** Compare device I/O with ordinary files.

The VFS you met in B1 exposes more than ordinary files. Here you distinguish **physical hardware** from **device files**, the OS interfaces through which applications access devices. A path such as `/dev/gpio/...` is not a physical circuit; it is the name of an OS-provided access point.

Begin with read-only observations. The [pin assignment reference](../../reference/hardware/PINS.md) describes physical wiring constraints, while the [device reference](../../reference/devices/DEVICES.md) describes paths and API behavior. Both are needed to safely operate hardware.

## B5.1 List devices safely

```text
piconix# ls /dev
piconix# ls /dev/gpio
piconix# pins
piconix# cat /proc/fb
```

Start with read-only inspection; no external circuit is required. `/dev` exposes device operations, while `/proc` presents system state.

**Limits of observation:** `cat /proc/fb` reports framebuffer data, but does not prove the LED matrix is wired correctly. Hardware experiments are **optional**. On a properly connected circuit, follow the [device guide](../../reference/devices/DEVICES.md) for `fbctl`, GPIO, PWM, and I²C. Printing text to a terminal is not the same as controlling an actual pin.

## B5.2 Read/write and ioctl

### Classify what you are looking at

| Source | Meaning | Question to ask |
|---|---|---|
| `/dev` | Device access points exposed by the OS | What does this name control? |
| `pins` | Pin assignments | Which function uses each GP number? |
| `/proc/fb` | OS-side framebuffer state | Why does this not prove correct wiring? |
| `reference/hardware/WIRING.md` | Physical connection requirements | Are voltage and component limits satisfied? |

First run `ls /dev`, record the result, and compare it with `pins`. Only operate an external LED after verifying safe wiring and that the pin is not reserved. Writing a GPIO value is an OS operation; the visible result depends on the physical circuit.

Some device functions fit normal `open()`/`read()`/`write()` semantics. Configuration such as pin direction or mode may need `ioctl()`. The VFS forwards operations to device-specific code.

## B5.3 Verify wiring before hardware tests

Consult the [pin assignments](../../reference/hardware/PINS.md), [wiring](../../reference/hardware/WIRING.md), and [devices](../../reference/devices/DEVICES.md) references before controlling GPIO, PWM, I²C, or an LED matrix. Observe pin reservations and voltage limits. Reading existing virtual files is enough to complete the required lesson.

## B5.4 Practice and check

**Guided experiment:** (1) List `/dev` and `/dev/gpio`; (2) use `pins` to see assignments; (3) separately list the OS framebuffer state and any physical wiring requirements. **Exit check:** “Which device file?”, “Which physical pin?”, and “Which driver function?” are different questions even if no external hardware is attached.

Compare a stored `/tmp` file with `/proc/fb`.

1. Where does their information come from?
2. Are `/dev` and `/proc` both ordinary persistent files?
3. Why do device operations require wiring and safety checks?

Learning record: Write down **what you ran / what you observed / why it happened**.

### A safe first observation

```text
piconix# ls /dev
piconix# cat /proc/devices
piconix# cat /proc/uptime
```

List virtual paths before trying electrical I/O. `/proc/uptime` needs no external wiring. Before driving GPIO, read [Pins](../../reference/hardware/PINS.md) and [Devices](../../reference/devices/DEVICES.md). To create a new software device, use the [virtual-driver lab](../../development/drivers/DRIVER-DEVELOPMENT.md).
