## B6.1 Hardware and security

This **optional chapter requires Pico W**. Telnet, HTTP, and other small teaching services have limited security. Use only an isolated lab network, never a public or Internet-facing setup. You may skip directly to Part C.

## B6.2 Inspect Pico W

Run **inside PicoNIX**:

```text
piconix# net
piconix# ip addr
piconix# cat /proc/net/wifi
piconix# ps
piconix# lsof
```

Identify the Wi-Fi mode, IP address, server processes, and sockets.

## B6.3 Access from a Linux PC

On a **Linux host connected to the Pico W AP**, using the real device IP address, for example:

```sh
curl http://192.168.4.1/
```

`curl` runs on the host PC, **not** on PicoNIX. `httpd` is a user-space server; the Telnet TCP 23 and remote-device UDP 2000 services run in the kernel.

## B6.4 Practice and check

### B6 extra lab: Telnet, network state, and loopback

In typical AP-mode setups Pico W has address `192.168.4.1`, while the DHCP client PC receives `192.168.4.2`. **Verify actual addresses using `ip addr` and `cat /proc/net/wifi`**, and read the device-specific SSID from the boot output. Stop if you cannot identify the correct lab network.

On a **Linux PC connected to the AP**, run the following and compare `ps` inside the Telnet session with `ps` over USB. Quit the PC Telnet client with `Ctrl+]` followed by `quit`.

```sh
telnet 192.168.4.1
```

On PicoNIX, inspect `net -r` and `cat /proc/net/memory` to observe ARP and network resources. An empty ARP table is not necessarily a failure. If `httpd` is running, you can also try `nc 127.0.0.1 80` **inside PicoNIX** to connect to the same device. An HTTP request requires `GET / HTTP/1.0` followed by an empty line; terminal newline differences may affect the result.

### B6 extra lab: Observe packets with `tcpdump`

Start the following on the Pico W's USB console, then generate traffic from a different **Linux PC** using `curl http://192.168.4.1/` (example AP address only).

```text
piconix# tcpdump -x -c 20
```

`tcpdump` summarizes the PicoNIX device's own IPv4 TCP/UDP/ICMP packets. `-c N` stops after N packets; `-x` adds payload length and up to 16 leading bytes in hexadecimal and ASCII. **Unlike Linux `tcpdump`**, it cannot capture arbitrary Ethernet frames or other devices' traffic, or save pcap files. An **illustrative output format**, not a measured capture:

```text
RX TCP 192.168.4.2:52000 > 192.168.4.1:80 LEN=60 DATA=16 ACK PSH
    DATA:  47 45 54 20 2f 20 48 54 54 50 2f 31 2e 30 0d 0a | GET / HTTP/1.0..|
```

`RX`/`TX` mean receive/transmit, `LEN` is the whole IPv4 packet size, and `DATA` is the length excluding protocol headers. The second line appears only when payload exists. Compare `SYN`, `ACK`, and `PSH` flags to study connection setup and data flow. The 16-record ring buffer can overwrite older records; Ctrl+C stops capture when traffic is insufficient.

From another PicoNIX terminal you may try `ping -c 2 192.168.4.1` and compare ICMP Echo Request (TYPE=8) with Echo Reply (TYPE=0). Work **only on an isolated lab network you control**. See the [network reference](../../reference/network/NETWORK.md) for more detail.

**Check:** Distinguish IP address from port, user-space `httpd` from kernel Telnet, TCP from ICMP, and what `net` versus `tcpdump` observes.
