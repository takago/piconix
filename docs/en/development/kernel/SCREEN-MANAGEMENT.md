# Screen Management Module

*Kernel implementation and reading guide — `kernel/screen.c`, `kernel/screen.h`*

PicoNIX screen management is a **kernel module**, not a user process. It does not occupy one of the six user task slots. TTY/PTY code transports terminal bytes, while `screen.c` maintains 80×24 character screens, interprets a subset of ANSI sequences, incrementally repaints the CDC consoles, and interprets screen-control keys.

## 1. Responsibilities and boundaries

| `screen.c` / `screen.h` | `kernel.c` and other code |
|---|---|
| `vt_screen_t`, `pty_screen[]`, `cdc_screen[]` | PTY Master/Slave FDs, references, and byte rings |
| `screen_byte()` ANSI screen interpretation | TTY input queues, line editing, wakeups |
| `screen_read()` screen stream generation | `/dev/pts/N.screen` VFS routing and FD position ownership |
| `screen_key_decode()` `.key` command decoding | Delivering decoded bytes to the PTY and reporting errors |
| `screen_cdc_poll()` incremental repaint | USB CDC TX ring and `console_queue()` |
| `screen_cdc_key_feed()` key classification | TTY delivery, console switching, shell creation |

The screen module does **not** spawn processes, allocate FDs, or resolve VFS paths.

```text
 sh / vi / games
       | read/write
       v
 TTY / PTY / VFS (kernel.c) ---- USB CDC TX queue
       |       ^                     ^
       v       |                     |
    screen.c --+--- rendered bytes --+
 ANSI / screen state / key decoding
       ^
 /dev/pts/N.screen and /dev/pts/N.key (via VFS)
```

## 2. Screen state and ANSI handling

`vt_screen_t` holds `cells[24][80]`, packed inverse-video bits, cursor position, CSI parsing state, and a `revision` counter. `pty_screen[SCREEN_PTY_COUNT]` and `cdc_screen[SCREEN_CDC_COUNT]` each hold two screens: **four screen states in total**, not four simultaneously visible panels.

`screen_reset()` and `screen_clear()` initialize screen state. `screen_byte()` consumes terminal output one byte at a time. On an `ESC[6n` cursor-position query it reports that a reply is needed; `screen_cursor_report()` in `kernel.c` delivers that reply to the appropriate TTY input queue. ANSI support is intentionally limited, not a complete terminal emulator.

**Reading path:** `vt_screen_t` in `kernel/screen.h` → `screen_reset()` → `screen_byte()` → `pty_screen_byte()` and CDC output handling in `kernel/kernel.c`.

## 3. PTY `.screen` and `.key`

These are VFS device nodes; `screen.c` does not own their file descriptors.

### `.screen`: reading display state

`pty_screen_read()` in `kernel.c` passes the selected screen and per-FD stream offset to `screen_read()`, which emits the 80×24 text screen with inverse-video SGR 7/0 and cursor underline SGR 4/24 where appropriate. Consecutive reads use the caller-owned FD offset. A read is not an atomic snapshot if the screen changes during transfer.

### `.key`: input instructions

`pty_key_write()` in `kernel.c` calls `screen_key_decode()` and then passes the validated byte sequence to `pty_master_rw()`. **Each `write()` is one complete command**; separate writes are not concatenated.

```sh
echo 'text:ls\n' > /dev/pts/0.key
echo 'key:ENTER' > /dev/pts/0.key
echo 'key:CTRL_C' > /dev/pts/0.key
cat /dev/pts/0.screen
```

- `key:` accepts a printable single character or a named key such as `ENTER`, `ESC`, `UP`, or `CTRL_A` through `CTRL_Z`.
- `text:` decodes `\n` as LF and `\\` as a literal backslash. Other backslash escapes are invalid.
- One trailing LF (and the immediately preceding CR, if present) is stripped as the command terminator, allowing `echo` to be used. Use `text:ls\n` to submit a command with LF.
- Decoded output is limited to 127 bytes. Invalid commands return `OS_EINVAL` before writing any bytes to the PTY. PTY input-buffer congestion can still cause partial acceptance.
- The corresponding PTY Master and Slave must be open; PTY number 0 is not necessarily in use.

See the [PTY device reference](../../reference/devices/PTY.md) for the complete command syntax and supported keys.

## 4. CDC virtual-console repaint

`cdc_screen[0]` and `cdc_screen[1]` retain independent screen state. `cdc_active` and `cdc_dual_mode` select the active console and single/dual-panel presentation.

1. `screen_cdc_begin_repaint()` starts a repaint.
2. `screen_cdc_poll()` generates limited output during idle-side polling.
3. The `screen_cdc_emit_t` callback routes generated bytes through `console_queue()` in `kernel.c` to the USB TX ring.
4. If the queue cannot accept all data, repaint pauses and resumes in a later polling pass.

The current implementation limits emitted output to **96 bytes per polling pass**. Preserve queue backpressure, background-screen revision checks, and repaint continuation when editing this code.

## 5. CDC key handling and shell creation

`screen_cdc_key_feed()` and `screen_cdc_key_timeout()` classify ordinary input and screen controls such as `Ctrl+T`, `Ctrl+G`, and `Ctrl+arrow`. Incomplete escape sequences retain the originating TTY, and timeout handling flushes unresolved input.

`screen_cdc_key_result_t` provides bytes to pass through, the original TTY, and an optional action. `cdc_key_dispatch()` in `kernel.c` delivers bytes and performs the requested console operation. **`cdc_vconsole_switch()` in `kernel.c` decides whether a second shell is needed and calls `spawn_in_slot()`; the screen module does not spawn tasks.**

## 6. MCP integration

`mcpd` is a user-space application. `terminal_send` sends ordinary `text` through the existing PTY Master path; named `key` input uses the `.key` path. HTTP and MCP JSON handling remain outside `screen.c`.

## 7. Regression checklist

- Check `kernel/screen.c` in the CMake build and exported types in `screen.h`.
- Verify scrolling, cursor movements, inverse video, and `.screen` stream offsets.
- Test `key:`/`text:` commands, invalid escapes, and the 127-byte limit.
- Test CDC `Ctrl+T`, `Ctrl+G`, `Ctrl+arrows`, standalone ESC, dual-panel switching, and repaint backpressure.
- Verify MCP `terminal_send` (`key` and `text`) and `terminal_read`.
- Build with Pico SDK 2.3.1 and inspect the kernel 56 KiB region, 24 KiB user slots, and ROM size.
